# AI 服务器运维与内网穿透平台总体规划

2026-11-03 · 状态：开发前规划 · 面向自用、单管理员、可管理多台 Linux 服务器

建设一个统一服务面板。选中一台服务器后，用户能看到它运行哪些服务、这些服务从哪里可以访问，并能让 AI 检查问题或执行已确认的变更。SSH 用于管理 Linux；端口转发和 P2P 直接沿用 gostc-open 的实现。两者在同一个面板里操作，各自保留自己的凭据和执行方式。

首个可用版本的目标：**从手机或桌面选中一个内网服务，让 AI 检查它的公网映射、修改目标端口，并拿到外部实测结果。** 定时巡检和 AI 部署随后接入，复用同一份服务档案与任务记录。

## 一、用户在面板里怎么用

桌面固定三栏。左边是历史会话，可搜索和新建，底部固定「设置」；中间默认是会话窗口，顶部选择服务器、环境、服务和模型，可切换「服务监控」「端口转发与 P2P」「巡检报告」；右边固定 SSH 密钥导入、绑定和测试连接。**选中某个服务是所有视图共用的操作**，从异常报告回到会话不用重选；切换服务器会使原目标上未执行的确认失效。

手机 App 使用同一控制服务端。首页按服务器进入服务详情，分屏展示会话、监控、转发、报告与连接设置；可导入密钥、操作规则、确认部署和查看任务。桌面发起的任务可在手机继续查看。退出客户端不终止已开始的任务。

| 用户要做什么 | 面板应给出的结果 |
| --- | --- |
| “这台机器上跑了什么？” | 展示发现的 systemd 服务、Docker 容器、监听端口，以及哪些服务已经登记健康检查和转发入口。 |
| “订单服务从外面能打开吗？” | 分别显示服务状态、目标响应、转发配置和公网实测；没有外部证据时写明未验证。 |
| “把公网 18080 的目标端口从 8080 改为 8081。” | 定位唯一规则，展示前后映射、涉及的协议和影响；确认后下发，只对这条规则验证并记录结果。 |
| “把订单服务更新到指定版本。” | 读取现有档案、核对现场、给出部署与回退计划；确认后通过 SSH 执行，验证后更新档案。 |

## 二、系统怎样组成

| 组件 | 部署位置与职责 |
| --- | --- |
| 控制服务端与数据库 | 部署在独立于被管机器的位置。管理身份、服务器与服务档案、会话、任务、报告。首版用一个后端和持久化任务记录，无需将每项功能拆成独立微服务。 |
| AI 控制器与任务执行器 | 控制器选择已登记的工具，执行器校验权限、目标和确认记录。SSH 动作走 SSH 执行器；转发动作调用裁剪后的 gostc 管理服务。 |
| gostc 公网节点与客户端 | 公网节点负责监听映射和协调 P2P；内网客户端主动连出，把流量送到目标服务。P2P 访问方也运行客户端。管理端和公网节点可同机，角色仍独立。 |
| 公网探测节点 | 从目标网络之外探测已登记的入口。控制服务端处于合适的外部网络时可兼任；否则单独配置。没有外部节点仍可检查本机和后端，但不能签发公网验证结果。 |

**复用与新建的分界：** 复用 gostc-open 的规则管理、节点、客户端、鉴权、ARPC 配置下发及其封装的 frps/frpc；新建统一服务面板、服务器与内网客户端的关联、AI 工具、SSH 执行、任务确认和巡检报告。网页按钮与 AI 走同一套服务端规则动作。规则由 gostc 管理服务保存，运维档案只引用规则编号和带时间的验证记录，避免两套配置互相覆盖。

## 三、端口转发与 P2P

**公网端口转发。** 按 gostc-open 原实现，一条规则同时生成相同端口的 TCP 和 UDP 代理。配置包含公网节点、内网客户端、公网端口、目标地址和目标端口。普通访问者直接连接公网入口。修改目标时，确认卡应明确两种协议都会改变；验收按目标服务实际支持的协议分别做，不能用一次 TCP 握手证明 UDP 正常。

**私有 P2P。** 两端通过 gostc 客户端接入，访问方使用该隧道的访问密钥，通过本机监听端口访问对端 TCP 服务。沿用 XTCP 打洞；仅当隧道允许中继且节点未禁止时，使用原有 STCP 回退。界面区分“等待连接、直连、中继、失败、路径未确认”。客户端在线、本地端口已监听，都不能单独证明已经直连。

**裁剪范围。** 转发模块只保留端口转发和 P2P；去掉注册、积分、套餐、计费、限速及其他代理业务。保留节点登记、凭据校验和端口占用检查，将原有套餐依赖与必要校验分开。宝塔、系统防火墙及网站反代保留只读检查，不混入 gostc 规则的修改和删除入口。

实施基线：[gostc-open 固定提交](https://github.com/SianHH/gostc-open/tree/16671e05b8c0e5d32db0146db862bc71c35e39ee)；关键路径：[转发与 P2P 配置下发](https://github.com/SianHH/gostc-open/blob/16671e05b8c0e5d32db0146db862bc71c35e39ee/server/service/engine/arpc.client.engine.go)、[P2P 访问端中继条件](https://github.com/SianHH/gostc-open/blob/16671e05b8c0e5d32db0146db862bc71c35e39ee/server/service/public/frp/service.visitor.p2p.go)。

## 四、AI 可以做什么

| 级别 | 动作 | 执行要求 |
| --- | --- | --- |
| 只读检查 | 列出规则、核对配置和回执、检查节点和服务、查看脱敏日志、探测登记的公网入口、生成报告 | 受限权限直接执行，逐项给出证据和时间。只读模式不能发出变更。 |
| 转发变更 | 创建、修改、启用、停用、删除面板托管的 gostc 转发规则 | 用户确认具体计划后，服务端复核规则编号、版本、节点和端口占用。删除前列出完整映射和受影响服务；不删除服务或其他隧道。 |
| SSH 部署 | 按支持的部署方式更新选定服务、检查健康状态、执行计划中已明确的回退 | 使用部署专用账号。首种建议支持 Docker Compose；没有可用回退时，在确认前写明。模型不可直接取得私钥或任意 root shell。 |

**模型控制。** 设置页管理模型地址、兼容中转地址、API Key、容量、工具能力和默认模型；会话中可切换模型。切换后重新计算上下文预算，保留历史，但不增加权限。不能调用工具的模型只解释结果。

**上下文控制。** 本轮只加载当前服务器和服务的必要档案、关联规则、近期对话和脱敏证据。用户可查看来源和采集时间、移除可选材料、固定“仅检查”等约束。接近容量上限时先裁剪日志，再压缩旧对话；当前目标、已确认计划和未完成任务保留。日志是待分析数据，不能覆盖用户指令。

**确认与恢复。** 检查不弹确认；写操作只确认具体差异。名称含糊或同端口存在多条规则时先定位目标。任一端修改了规则或切换目标后，旧确认失效。任务有唯一编号；断网、重复点击、切换模型时查原任务，不重复执行。已保存、已下发、客户端已应用、业务已验证分别显示；离线删除标记“待撤销”，不提前报成功。

## 五、密钥、服务档案与运行状态

SSH 私钥由用户手动从文件导入，口令通过单独输入框提交；加密保存，解密主密钥与数据库分开保管。按主机、账号和用途绑定，支持替换和停用；首次连接核对主机指纹，变化时暂停。支持直连或已有 SSH 跳板，目标私钥不复制到跳板机。定时巡检使用受限凭据。模型 API Key、节点令牌、P2P 密钥和 SSH 私钥分别保管，聊天、报告和操作历史仅持有必要引用。

| 记录 | 保存内容 | 何时更新 |
| --- | --- | --- |
| 服务档案 | 服务器、环境、服务名、部署方式、版本或镜像摘要、目录、端口、配置路径、健康检查、关联规则和回退版本 | 有验证证据才更新“最近成功状态”；当前预期配置可以不同。 |
| 规则与执行任务 | 规则编号、节点、客户端、映射、配置版本；任务记录操作者、确认内容、步骤、回执和结果 | 配置变更、下发和探测分别记录。删除规则保留其历史，不复用旧确认。 |
| 监控与报告 | 指标、服务状态、分项结论、探测来源、时间、异常与恢复 | 随采集或巡检追加。清空会话不影响服务档案、任务或报告。 |

例如部署 v1.3 后健康检查失败，档案仍保留 v1.2 的上次成功记录，当前现场标为“待核实”；只有确认回退且验证成功，才显示“当前运行 v1.2”。次日开新会话，AI 应先读档案，再核对服务器。

## 六、监控、巡检和宝塔检查

监控面板展示 CPU、负载、内存、磁盘、网络趋势及最后采集时间；服务视图把进程、应用健康和公网入口分开展示。SSH 断连保留上次数据并标记过期。支持手动巡检、定时巡检和部署后针对性检查。报告列出异常、正常、未验证项及与上次相比的变化；持续故障不重复提醒，出现异常或恢复时通知手机。

以“公网 8443 无法访问”为例，先确定入口由谁管理，再按链路查：

1. **配置来源：** gostc 读取托管规则和版本；宝塔按目标版本读取其端口转发配置，无法读取就标“宝塔配置未核实”。单纯放行端口或配置网站反代不等于建立了端口转发。
2. **实际生效：** gostc 检查客户端回执及节点状态；宝塔对照系统实际防火墙或 NAT 规则。不能仅凭存在一条系统规则认定由宝塔创建。
3. **后端响应：** 从能够访问目标的客户端或转发机发起协议检查。记录拒绝、超时或实际响应；不要把服务进程存在等同于业务正常。
4. **公网结果：** 外部节点检查登记入口。TCP 区分握手与预期业务响应；UDP 用已知请求和对应响应测试，无响应标“未确认”。缺少外部节点则标“公网未验证”，不推断云安全组一定有问题。

报告中的「交给 AI」把当前服务器、规则和对应证据带进会话。AI 可以拟定修复方案，但读报告本身不会触发变更。

## 七、建设顺序与交付门槛

| 阶段 | 交付范围 | 进入下一阶段前必须证明 |
| --- | --- | --- |
| 1　建面板与接入 | 单管理员、桌面三栏、服务器和服务档案、SSH 手动导入、连接测试 | 在一台测试机读取服务状态；错误主机指纹会阻止连接。SSH 连不上时仍能在面板查看历史。 |
| 2　接入 gostc | 内置节点和客户端登记、转发规则、P2P、手动启停及删除 | 同一条映射实际完成 TCP 与 UDP 往返；两个独立 NAT 网络分别验证直连、允许回退及禁止回退。仅本机连通不算 P2P 验收。 |
| 3　完成首个可用版本 | AI 会话、模型和上下文设置、规则只读检查和写入工具、手机端规则页与任务确认 | 桌面发起目标端口变更，手机确认，外部探测命中新目标；重复提交只执行一次，过期确认不能删除规则。 |
| 4　加入监控与巡检 | 指标趋势、服务健康、宝塔检查、历史报告和异常通知 | 保留宝塔规则并停止后端，报告能同时显示规则存在、后端异常和公网业务验证失败；恢复后记录恢复。 |
| 5　加入 AI 部署与记忆 | 首种部署方式、计划确认、执行、健康检查、回退和档案更新 | 成功部署后新会话能定位服务；故意引入失败版本不会覆盖上次成功记录。关掉客户端后仍可恢复原任务。 |

**联调条件。** 准备一台公网测试节点、一台能访问目标服务的内网客户端、处于另一网络的访问端、一个外部探测位置，以及可安全停止和回退的测试服务。宝塔兼容性按实际版本验证。没有相应网络、账号或设备时，记录未验证项，不把模拟结果列为线上通过。

**发布原则。** 对当次修改及直接影响的路径做必要检测；按项目约定核对发布目标和差异，发布后验证对应线上行为，再提交并推送 GitHub。以上为后续实施标准，本次交付仅为总体规划。
