# 端口转发与 P2P 内网穿透工具需求

**实施基线：从 [SianHH/gostc-open](https://github.com/SianHH/gostc-open/blob/16671e05b8c0e5d32db0146db862bc71c35e39ee/README.md) 的开源实现裁剪。** 只保留「端口转发」和「P2P」两个业务入口，沿用原项目的网页配置、服务端下发、节点及客户端执行机制。本文是开发与验收要求；基线提交为 `16671e05b8c0e5d32db0146db862bc71c35e39ee`。

本模块内置在 [Linux 服务器 AI 运维平台](Linux服务器AI运维平台需求文档.md) 的服务面板中。用户选择服务器后即可管理规则，也可让当前 AI 会话操作同一条规则，无需再登录独立的 gostc 管理后台。

## 1. 使用方式

| 功能 | 配置示例 | 访问方式 |
| --- | --- | --- |
| 端口转发 | 在公网节点将 18080 映射到内网客户端可达的 `192.168.1.20:8080`。按原实现，一条规则同时为相同端口生成 TCP 和 UDP 代理。 | 访问者无需安装客户端，直接连接公网节点的 18080。业务流量经节点转发；实际能收到哪种协议的响应，取决于目标服务。 |
| P2P | 给该内网 TCP 服务建一条 P2P 隧道。访问者在自己的 gostc 客户端输入访问密钥，指定本机入口，如 `127.0.0.1:18080`。 | 访问本机入口，优先通过 XTCP 打洞直连。规则允许中继且节点未禁用中继时，可回退到 STCP；两种路径均不要求将该业务端口公开给普通访问者。 |

## 2. 保留的组件

- **管理端：** 保留原 `web` 中转发与 P2P 的表单和列表，以及 `server` 的规则存储、节点和客户端登记、鉴权及 ARPC 配置下发。自用版保留一个管理员；手机和桌面浏览器使用同一面板。
- **公网节点：** 运行节点模式的 gostc（`-s`）。通过原 `server_config` 处理器接收配置，在进程内启动项目封装的 frps。管理端与节点可部署在同一台公网 Linux 上，仍保留两个角色。
- **内网客户端：** 运行客户端模式的 gostc，接收控制端下发的规则，使用原项目锁定的 `github.com/SianHH/frp-package` 在进程内启动 frpc。P2P 访问侧使用原 visitor 实现。用户不需要另外安装原版 frps/frpc 或手写 TOML。
- **裁剪边界：** 保留节点与客户端的连接凭据、隧道鉴权和端口占用校验。移除用户注册、套餐购买、积分、计费、限速及其他代理类型。创建规则时将节点和端口校验与套餐资格解耦。AI 会话、模型控制、权限、任务和巡检报告共用现有运维平台的设计；转发模块不重复建设这些功能。

## 3. 端口转发流程

1. 管理员选择公网节点和内网客户端，填写名称、公网端口、目标地址及目标端口。端口按 TCP 和 UDP 两种协议检查；冲突时指出节点、协议和端口。
2. 沿用 `ForwardConfig`：服务端根据同一条记录构造 TCP、UDP 两份代理配置，以同一规则标识通过 ARPC 消息 `forward_config` 下发。
3. 客户端用规则标识和 `UpdateTag` 判断是否重复；配置有变化时替换该规则的旧实例，调用原封装启动新实例并回执。配置保存、客户端已应用、外部业务验证是三个不同结果。
4. 面板和 AI 均可创建、编辑、启停和删除规则。客户端离线或未回执时显示“待应用”或“待撤销”；仅在证据确认后标记运行状态。停用或删除生效后，该规则不得再接受新连接。

### 3.1 面板和 AI 如何管理同一条规则

桌面中栏和手机服务详情均提供「端口转发」。列表显示来源、规则编号、关联服务、公网节点与入口、内网客户端及目标、配置状态、最后验证时间。每行提供「检查」「修改」「启用／停用」「删除」和「交给 AI」；也可直接在会话下指令。平台用服务器、节点、客户端及规则编号定位目标，同名或同端口匹配多条时先列出候选项。宝塔和系统发现的规则标注来源，只提供检查，不通过 gostc 接口修改。

| 用户指令示例 | 服务面板与 AI 的行为 |
| --- | --- |
| “检查订单服务的 18080 转发是否正常” | 只读核对规则及下发回执、节点与客户端是否在线、目标服务是否响应，再按已登记协议做公网探测。逐项列出来源和时间；没有外部探测结果就标“公网未验证”。 |
| “给订单服务新增一条 18080 映射并启用” | 列出节点、内网客户端、目标地址，以及同一公网端口将同时映射 TCP 和 UDP；校验占用后展示计划，确认后创建并应用。 |
| “把 18080 的目标端口从 8080 改为 8081” | 展示修改前后映射和受影响服务；确认后只更新指定规则。用新连接和目标业务响应核验，旧回执不能证明新版本已生效。 |
| “先停用这条映射”或“重新启用它” | 显示将停止或恢复的入口；确认后变更启用状态，保留映射配置。停用检查不再接受新连接，启用检查目标业务可达。 |
| “删除这条转发” | 确认卡列出规则编号、完整映射和影响，说明删除会移除配置。确认后撤销该规则，保留脱敏操作记录；不删除目标服务、其他映射或 P2P 隧道。 |

**执行与记录。** 面板按钮和 AI 调用同一组服务端动作，对应 gostc-open 的 [规则管理路由](https://github.com/SianHH/gostc-open/blob/16671e05b8c0e5d32db0146db862bc71c35e39ee/server/router/normal/gost_client_forward.go)（page、create、update、enable、delete）。检查由平台聚合只读证据。模型不直接改数据库，不用 SSH 绕过规则管理。服务端校验操作者权限；确认绑定具体动作、目标和配置版本，规则被另一端改动后须重新预览。重复点击或模型重试复用已有任务，不重复创建或删除。

**会话、巡检与记忆。** 转发操作沿用当前模型和“只检查”约束；不向模型传送节点令牌或访问密钥。检查结果可写入巡检报告。变更任务记录操作者、前后映射、回执和验证结果；关联服务档案分别保存预期配置与最近一次已验证状态。待应用或待撤销时保留该差异，换设备或新建会话后仍可查询。

## 4. P2P 流程及中继条件

1. 管理端保存 P2P 隧道、目标 TCP 服务和访问密钥，保留原有的隧道中继开关与节点禁用中继设置。提供端通过 `p2p_config` 接收 XTCP 配置；仅在允许中继时附带 STCP 配置。
2. 访问端沿用原 visitor：凭访问密钥向 `/api/v1/public/frp/visitorP2P` 获取对应配置，绑定本机地址与端口。访问密钥不得出现在访问日志或错误详情中。
3. **允许中继：** 隧道开启中继且节点未禁用时，沿用基线的 XTCP → STCP 回退设置（等待 1500 毫秒）。直连成功，数据走两端；触发 STCP 回退，数据走公网节点。
4. **不允许中继：** 隧道未开启中继，或节点已禁用中继时，服务端移除 STCP 配置并清空回退目标。打洞未成功时报告失败或等待重试，不额外建立公网映射。
5. 界面区分「配置已应用」和「实际连接路径」。有建链证据才显示直连或中继；没有路径证据时显示未确认。客户端在线或本地端口已监听都不能证明打洞成功。

## 5. 针对性验收

| 场景 | 通过标准 |
| --- | --- |
| 无套餐配置规则 | 单管理员可登记节点与客户端并创建两类规则；未授权的客户端或访问密钥仍不能使用对应隧道。 |
| 一条规则转发两种协议 | 在同一目标端口准备 TCP 与 UDP 回显服务，只创建一条映射；从公网分别发出两种协议的已知报文，收到各自预期的响应。 |
| 规则更新与停用 | 修改目标后新连接到达新目标；重复下发同一版本不会重复启动；重连后已启用规则恢复、已停用规则不恢复。 |
| P2P 直连 | 两个不同 NAT 网络中的客户端访问成功，结合 XTCP 建链记录核对直连；错误访问密钥不能建立新连接。 |
| P2P 回退 | 在无法打洞但能到达节点的环境中，同时允许隧道及节点中继时，业务可经 STCP 访问；记录中继路径，不标为直连。 |
| 禁止回退 | 分别测试“隧道关闭中继”和“节点禁止中继”。两种情况下均不下发有效回退配置；打洞失败时不能经 STCP 或公网映射访问。 |
| 面板与 AI 操作同一条规则 | 桌面用 AI 新建转发，手机在同一服务下看到该规则；手机修改目标后，桌面 AI 能读到新配置并检查实际响应。依次停用、启用、删除，核对新连接和任务记录，其他映射及 P2P 隧道不变。 |
| 权限与状态冲突 | 只读巡检不产生写操作；未确认删除不下发；在另一端改动规则后，旧确认失效。客户端离线时不报告撤销成功，重复提交不产生第二项变更。 |
